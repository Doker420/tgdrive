# Siteflow Studio: серверная основа

**Это не готовый к продакшну продукт.** Реализована серверная основа и интеграционные адаптеры, но полноценный конструктор, загрузка пользовательских сайтов, формы заявок и интеграции Telegram/VK отсутствуют. Реальное развёртывание, проверка на целевом сервере, тесты с реальным PostgreSQL и API-ключами, аудит безопасности, эксплуатационная настройка и проверка лицензий источников ещё необходимы. Не используйте текущую версию для коммерческого сбора до выполнения этих работ.

## Что реализовано

- Один администратор: сессии в PostgreSQL, HttpOnly/SameSite cookie, ограничение частоты входа, проверка Origin для изменяющих запросов. Создание аккаунта и смена пароля через интерфейс не реализованы.
- Одна кампания, карточки компаний, CSV-импорт, поиск, фильтры и отметка отправки. Данные хранятся в PostgreSQL. Прежние примеры не импортируются автоматически. Заметки пока хранятся только до перезагрузки.
- Демо на `/demo/<случайный UUID>` с актуальными данными из БД; это всё ещё **один встроенный шаблон**, не редактор пользовательских сайтов. Всякий, у кого есть ссылка, видит демо. Нет управления публикацией или отзыва ссылки.
- Серверные адаптеры для Google Places Text Search, Яндекс Places HTTP API и 2ГИС Places API; запрос ограничен 60 компаниями. Пустые API-ключи дают явную ошибку. Контакты, тарифы и результаты зависят от доступа к API. Описание — простая заготовка, а не генерация ИИ. Адаптеры тестировались с имитацией ответов, не с реальными ключами.
- Добавление собственного ZIP/HTML и автоматическая подстановка в произвольный шаблон не реализованы. Нельзя безопасно обслуживать недоверенные пользовательские HTML/JS на домене панели или существующего сайта без изоляции. Также нет редактора шаблонов, заявок, обработки лидов, подключения Telegram/VK и автоматической рассылки.

Перед подключением реальных данных проверьте условия каждого API, в особенности права на хранение, повторное использование, обязательную атрибуцию, стоимость и разрешённый маркетинг. Текущая реализация не обеспечивает автоматически соблюдение всех таких требований. API могут не предоставлять все контакты или ограничивать поиск и хранение данных.

## Конфигурация и пример развёртывания

Файлы `Dockerfile`, `compose.yaml`, `.env.example` и `deploy/nginx.example.conf` — отправная точка, **не подтверждение развёртывания**. `docker` и настоящий PostgreSQL в среде разработки не были доступны, Docker-сборка и настройки nginx не проверены. Конфигурацию существующего сервера нужно сначала изучить, сделать резервную копию и проверить на конфликты маршрутов. Не перезаписывайте сайт `stats-max.ru`.

1. На сервере установите Docker Compose и nginx (или адаптируйте пример под существующий веб-сервер). Создайте DNS A-запись `studio.stats-max.ru`, указывающую на сервер; для `stats-max.ru` используйте существующую запись, предварительно проверив, куда она указывает. Выпустите HTTPS-сертификаты и настройте обновление. Настройте firewall: публично открыты только необходимые порты 80/443 и администрирование, а порт 7777 слушает только localhost. Не отключайте рабочие сервисы и не открывайте PostgreSQL наружу.
2. На сервере в каталоге приложения скопируйте `.env.example` в `.env`, задайте длинный случайный `POSTGRES_PASSWORD` (используйте только буквы/цифры, чтобы URL подключения не потребовал экранирования), `ADMIN_USERNAME`, `STUDIO_ORIGIN=https://studio.stats-max.ru`, разрешения `chmod 600 .env`. Получить хеш пароля можно на доверенном компьютере с Node.js: `stty -echo; read -r PASS; stty echo; printf '%s\n' "$PASS" | node server/hash-password.mjs; unset PASS`. Используйте уникальный пароль длиной не менее 16 символов. Вставьте в `.env` только полученный хеш `ADMIN_PASSWORD_HASH`. Никогда не передавайте пароли или API-ключи в чате, коммитах или командной строке. Ротация хеша при перезапуске не отзываёт уже созданные сессии: при компрометации необходимо дополнительно удалить записи из таблицы `sessions`.
3. Задайте ключи `GOOGLE_PLACES_API_KEY`, `YANDEX_MAPS_API_KEY`, `TWOGIS_API_KEY` в `.env` после получения доступа к официальным API и проверки условий. Не передавайте их в браузер или репозиторий. Возможность получать контакты может требовать дополнительных разрешений, а Google API может требовать платёжную конфигурацию.
4. Запустите `docker compose up -d --build`, проверьте `docker compose ps`, журналы и `curl http://127.0.0.1:7777/api/health`. Порт 7777 привязан только к loopback. Используйте отдельный мониторинг и резервное копирование volume PostgreSQL; резервные копии надо регулярно проверять восстановлением.
5. Добавьте прокси для `studio.stats-max.ru` и **только после проверки конфликтов** маршруты `/demo/`, `/api/public/demos/`, `/siteflow-assets/` в существующий HTTPS virtual host `stats-max.ru` — пример в `deploy/nginx.example.conf`. Сначала `nginx -t`, затем reload. Нужны также HTTPS-редирект, корректные сертификаты и настройки заголовков на реальном сервере. Маршруты `/api/public/demos/` и `/siteflow-assets/` могут конфликтовать с существующим сайтом — до изменения конфигурации необходимо проверить это.

## Разработка и проверки

`npm install`, `npm run build`, `npm test`. Тесты API используют `pg-mem` и имитируют ответы поставщиков; они не заменяют проверку PostgreSQL, Docker, nginx, DNS, TLS и реальных API. Для ручной разработки настройте реальный PostgreSQL, `DATABASE_URL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`, `STUDIO_ORIGIN=http://localhost:5173`, затем запустите `npm run server` и `npm run dev -- --host 0.0.0.0`; Vite проксирует `/api` на локальный порт 7777. Продакшн-сборка Vite должна использовать корневой base `/`.
